# GraphQL.EntityFramework bug audit, second pass

Audit of the working tree at d7e9ccaa (2026-09-10), after the first pass's findings were all fixed and merged. Items tagged **ran** were reproduced with a throwaway probe test against the integration schema and LocalDB; **read** items were confirmed by tracing the cited code paths but not executed. Items ticked off say which branch fixed them.

## Confirmed by probes

- [x] **ran** Fixed on `navigation-arguments-in-sql`: `ids`, `where` and `orderBy` are now applied inside the collection subquery when the parent is projected, and evaluated in memory against whole entities otherwise. `where` and `orderBy` on navigation list and navigation connection fields ran against columns that were never loaded. The nested projection is built from the selection set only, so `children(where: {path: "property", comparison: equal, value: "Value1"}) { id }` projects children with just `Id` and `ParentId`, then filters in memory on a null `Property`. The probe returned an empty list for a matching child, and `orderBy: {path: "property", descending: true}` left the rows in key order. Root query fields are unaffected because their arguments become SQL. Fix in `src/GraphQL.EntityFramework/IncludeAppender.cs` (`ProcessNavigationOrScalar`, `ProcessProjectionExpression`): add the paths named by the field's `where` and `orderBy` arguments to the nested projection, including list paths such as `children[property]`, or mark the navigation whole whenever those arguments are present. Arguments can arrive through variables, so resolve them rather than reading the AST literally.
- [x] **ran** Fixed on `items-and-resolvelist`: the wrapper is recognised by the graph type the field is selected from. A navigation named `items`, `edges` or `node` was treated as a connection wrapper. `IsConnectionNodeName` in `src/GraphQL.EntityFramework/IncludeAppender.cs` matches by name alone, so an entity with an `Items` collection had it never projected: `items: []` and no join in the SQL. Only unwrap when the parent graph type is a `ConnectionType<,>` or `EdgeType<>`; `ProcessSelectionSet` and `GetLeafSelection` already have the parent graph type in hand.
- [x] **ran** Fixed on `items-and-resolvelist`: both apply the filters per item. `ResolveList` and `ResolveListAsync` in `src/GraphQL.EntityFramework/GraphApi/FieldBuilderExtensions.cs` skipped filters. Every other list path applies them. A filter rejecting one child had no effect through `ResolveList`, so this is an authorization gap. The comment in the method acknowledges it and the docs do not. Apply `Filters.ApplyFilter` the way `AddNavigationListField` does.
- [ ] **ran** The resolver-less navigation overloads are a trap on object graph types. `AddNavigationListField(name, projection)`, the connection overload and the single overload add `where`, `orderBy`, `ids`, `skip` and `take` but set no resolver, so GraphQL.NET's name resolver returns the raw property. A field named `children` returned both children with a `where` that matched one; a field named anything else threw "Expected to find property or method". They also skip filters. They exist for interfaces, where the object type supplies the resolver. On an object type either attach the resolver `AutoMap` uses or throw at registration. Overloads: `src/GraphQL.EntityFramework/GraphApi/EfGraphQLService_NavigationList.cs`, `EfGraphQLService_NavigationConnection.cs`, `EfGraphQLService_Navigation.cs`, and the wrappers on `EfObjectGraphType`.
- [ ] **ran** The first accessed path in a projection expression decides which navigation receives the field's selection set. With `projection: _ => new { _.Child2, _.Child1 }` resolving `Child1`, the selection under the field was applied to `Child2`, and `child1Second { parent { id } }` came back with `parent: null`; the SQL joined the parent onto the wrong child. See `primaryNavigation` in `ProcessProjectionExpression`, `src/GraphQL.EntityFramework/IncludeAppender.cs`. Apply the selection set to every navigation whose entity type matches the field's item type, not to whichever path the analyzer visited first.
- [x] **ran** Fixed on `navigation-arguments-in-sql`: the in-memory pass rewrites the call to a pattern match. `like` on an in-memory navigation list threw `The 'Like' method is not supported because the query has switched to client-evaluation`. The predicate calls `EF.Functions.Like` at `src/GraphQL.EntityFramework/Where/ExpressionBuilder.cs` (`MakeSingleStringComparison`), which cannot run outside a query. The list path in `ArgumentProcessor_List` needs an in-memory substitute, for example a visitor that swaps the call for a pattern match before compiling.
- [ ] **ran** Where values parse with the current culture. Under `de-DE`, `equal` with `"1.5"` on a decimal property did not match `1.5m`. `Convert.ChangeType` and the `int`, `long`, `short`, `DateTime` and `DateTimeOffset` parsers in `src/GraphQL.EntityFramework/Where/TypeConverter.cs` take no format provider. All of them should pass `CultureInfo.InvariantCulture`. The single-value date and time conversions go through GraphQL.NET's `ValueConverter`, so `equal` and `in` currently parse the same literal differently.

## Found by reading

- [ ] **read** `KeyNameExtractor` skips any entity whose assembly name starts with `System` (`src/GraphQL.EntityFramework/KeyNameExtractor.cs`). A user assembly such as `Systemic.Domain` loses every key: `ids` disappears from the schema and projected entities carry an empty `Id`. The intent is the join dictionaries EF creates for shadow many-to-many, so test `IsPropertyBag` or the CLR type instead of the assembly name.
- [ ] **read** Cursor paging deviates from Relay for `first` with `before` and for `last` with `after` (`src/GraphQL.EntityFramework/ConnectionConverter.cs`, `First` and `LastRange`). `first: 2, before: 5` returns items 3 and 4 rather than 0 and 1, and `last` after a cursor takes from the cursor forward rather than from the end. The `ConnectionConverterTests` snapshots lock in the current behaviour, so this may be deliberate; decide, and document it either way.
- [ ] **read** An empty connection reports `startCursor: 0` and `endCursor: -1` (`ConnectionConverter.Build`). Relay expects null cursors when there are no edges.
- [ ] **read** Derived-type fragments below a nested navigation lose their derived navigations. `GetDerivedNavigationsFromFragments` runs on the root selection only; a derived-only navigation under `parent { ... on Derived { nav { x } } }` reaches `ProcessNavigationOrScalar` with the base type's navigations, falls through to the scalar path and is dropped. Derived scalars in the same position do survive, through the type-test chain.
- [ ] **read** `skip` or `take` without `orderBy` adds an error to `context.Errors` and then still runs the query (`src/GraphQL.EntityFramework/Where/ArgumentProcessor_Queryable.cs`), so the response carries both nondeterministic data and an error. Return null or throw instead.
- [x] **read** Fixed on `navigation-arguments-in-sql`: the arguments now run in SQL where the parent is projected, and the remaining in-memory comparisons ignore case; documented in query-usage. In-memory string comparisons differed from SQL. `equal` is ordinal and case-sensitive in memory, and `contains`, `startsWith` and `endsWith` use culture-sensitive `string` methods, while the same `where` on a root field follows the database collation. A design limitation; worth a line in the docs.

## Perf

Nothing material. The one candidate measured, building and interpreting a `where` predicate once per parent row in `ArgumentProcessor_List`, costs about 4 µs per row, so caching it is not worth the complexity. The remaining per-row work is the argument conversion in `ArgumentReader.ReadList`, unmeasured but of the same order.
